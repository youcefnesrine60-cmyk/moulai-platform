التاريخ: 10 نوفمبر 2026. الحالة: **جاهز للمراجعة مع تحفظات قبل التفعيل**.

تم حفظ العمل السابق في GitHub، ثم إعداد مسار مستقل للاستضافة وتجربة ترحيل
حقيقية على مشروع Neon جديد خالٍ من بيانات الزبائن. لم يُنشر التطبيق ولم تُفعّل
استضافة مدفوعة. نجاح الترحيل والبناء لا يثبت اكتمال التكامل أو جاهزية الإنتاج.

## 4. الترحيل الذي نُفذ والأدلة

1. إعادة بناء محلية فارغة بواسطة `main-bootstrap-v1` وسلسلة Alembic الرئيسية
   الفعلية، دون تعديل المهاجرات التاريخية أو استعمال `stamp`.
2. التقاط أوامر الكتابة المنفذة فعليًا، وتجميع القيم المقيدة بواسطة أنواع
   SQLAlchemy، دون استبدال نصي تقريبي للمعاملات.
3. تقسيم الناتج إلى 391 أمرًا حتى S1a، ثم 141 أمرًا من S1a حتى O4.
4. إعادة تنفيذ الناتج على قاعدة محلية ثانية: تطابق المخطط والقيم المرجعية غير
   الزمنية. اختلفت ساعات التهيئة الجديدة على سبعة جداول؛ ليست سجلات اشتراك أو
   فواتير تاريخية ولا يُقدّم ذلك كاستعادة pg_dump مطابقة بايتًا ببايت.
5. تنفيذ مرحلة S1a في معاملة واحدة بواسطة موصل Neon الرسمي على الهدف الجديد.
6. إنشاء فرع استرجاع من S1a قبل الانتقال، ثم مقارنة بصمات الصفوف لكل الجداول الـ61.
7. تنفيذ الانتقال إلى O4 داخل savepoint، ثم التراجع ومقارنة كل البصمات: تطابق
   كامل. أُعيد تنفيذ الانتقال في المعاملة نفسها ثم جرى commit ناجح.
8. إعادة قراءة فرع الاسترجاع بعد الترحيل: بقي S1a وجميع البصمات مطابقة.
9. مقارنة كتالوج O4 البعيد مع البناء المحلي المنفذ: تطابق 974 عمودًا و1198 قيدًا
   و298 فهرسًا و77 trigger غير داخلي. يشمل عدد القيود تمثيل PostgreSQL 18 لـ NOT NULL.

مقارنة الكتالوج المقاسة لا تعني تحققًا شاملًا من كل ACL أو دور أو جسم function.
صلاحيات دور runtime المقترحة لم تُطبّق أو تُختبر بعد، ولا تشغيل للتطبيق البعيد.
الـSQL المولّد يحتفظ بكتابات إصدار Alembic الناتجة من تشغيل السلسلة الفعلية؛
لم تُستبدل مهاجرات بـكتابة يدوية لـ `alembic_version`.

أُزيلت المسافات في نهايات أسطر نسختَي SQL المعدّتين لـGit فقط. حُفظت بصمة المصدر
المجرّب وبصمة نسخة النشر في manifest مع تحقق تطابق تسلسل الكلمات؛ لا تعديل لأمر
أو قيمة أو ترتيب ولا ادعاء إعادة تنفيذ ملف مختلف منطقيًا.

تختلف أوقات `created_at`/`updated_at` في مراجع التهيئة الجديدة فقط، وأوقات
`effective_from`/`recorded_at` لسعر الأساس المنشأ لأول مرة. التفاصيل في
`sql-provenance.json`. لم تُضف أسعار ميزات خيالية أو صلاحيات شخصية أو cash.

## 6. ضمانات المضيف وحدودها

- لا قراءة `.env` من المشغّل ولا fallback إلى `DATABASE_URL` غير صريح. أسرار
  staging تُقرأ من أسماء مخصصة وتُضبط في العملية فقط.
- يتطلب اتصال runtime الدور المحدود والهدف المعين وTLS وهوية الخادم الحقيقية
  وعلامة القاعدة وإصدار O4. دور الترحيل غير مقبول كدور تطبيق.
- أصل HTTPS وrealm مستقل `moulai-staging`، callback محدد، PKCE S256، nonce/state،
  وتحقق التوقيع/issuer/audience/introspection الموروث. لا دخول بكلمة مرور مباشرة
  ولا استيراد حسابات محلية. الدعوات فقط في البداية؛ التسجيل الذاتي البعيد غير مفعّل.
- دور `moulai-staging-tester` يجيز دخول المضيف فقط. لا يمنح شركة أو مطعمًا أو إدارة
  أسعار أو بلد فوترة أو نقدًا. تبقى أذونات الأعمال في الخدمات والخادم.
- مسارات العملاء والـQR تتطلب أيضًا جلسة مختبر، ثم إثبات الزيارة المستقل المعتاد.
  هذا قيد مقصود في أول staging مغلق؛ تجربة عميل مجهول عبر QR ليست متاحة بعد.
- جلسة 300 ثانية دون تجديد تلقائي. لا يُحفظ مسودّ في السحابة أو localStorage لهذا
  الغرض. تدفق إعادة الدخول وحفظ/فقد السطور أثناءه يجب اختباره على الأجهزة بعد التفعيل.
- جلسات مشفرة على SQLite/قرص مخصص، عامل واحد فقط. المخطط لا يحاول تشغيل worker أو
  migration أو seed أو إشعار عند بدء التطبيق.
- حد اتصال Python يمنع مزودي IA وTelegram وRedis والبريد. هو دفاع إضافي، وليس
  بديلًا عن سياسة شبكة الاستضافة. تُثبّت عناوين DNS المسموحة عند البداية؛ تغيرها
  يستدعي إعادة تشغيل مضبوطة بدل توسيع الشبكة تلقائيًا.
- تتطلب Settings القديمة قيمة غير فارغة لمفتاح IA. تُستخدم في هذه العملية قيمة
  تعطيل صريحة مع endpoint `.invalid`، وليست مفتاحًا حقيقيًا. قد يكتب logger الموروث
  `enabled=true` عند إنشاء العميل؛ ذلك لا يثبت توفر IA. لا استدعاء مزود في الفحص.
- تُخفى query parameters من access logs في المشغّل لتجنب تسجيل OAuth codes.
  يلزم فحص سجلات proxy/Keycloak بعد التفعيل أيضًا.
- بعض وسوم DTO التقنية الموروثة مثل `postgres-local` بقيت للتوافق؛ هوية الجلسة
  الفعلية ووسم staging مستقلان. الإشعارات والمحاكاة المتبقية ليست تنفيذًا بعيدًا.

لم تُعد حملة اختبارات Backend العامة، ولم تُنفذ اختبارات هدّامة على التطوير البعيد.

أذونات runtime والأداء والموارد ضمن قائمة ما بعد التفعيل، لا ضمن PASS أعلاه.

## 9. الأسرار والإعدادات التي ستلزم

| العنصر | المصدر/الاستخدام المستقبلي |
| --- | --- |
| `MOULAI_STAGING_DATABASE_URL` | دور runtime محدود على القاعدة الجديدة فقط؛ لا دور الترحيل |
| `MOULAI_STAGING_OIDC_CLIENT_SECRET` | client سري في realm staging المستقل |
| `MOULAI_STAGING_SESSION_KEY` | مفتاح Fernet خاص، خارج Git ومع نسخة استرجاع آمنة |
| `MOULAI_STAGING_ORIGIN` / `ISSUER` / `CLIENT_ID` / `AUDIENCE` | قيم public صريحة ومتطابقة مع realm والـcallback |
| `MOULAI_STAGING_PROXY_CIDRS` | شبكات proxy الموثوقة فعليًا، لا `0.0.0.0/0` |
| `KC_DB_URL` / `KC_DB_USERNAME` / `KC_DB_PASSWORD` | قاعدة هوية جديدة منفصلة، لا قاعدة أعمال أو إنتاج |
| `KC_HOSTNAME` / `KC_PROXY_TRUSTED_ADDRESSES` | HTTPS وproxy محددان، دون hostname مرن |
| `KC_BOOTSTRAP_ADMIN_*` | اعتماد إعداد مؤقت خاص بالهوية، لا إذن أعمال تلقائي |

تُدخل القيم في مدير أسرار الخدمة بعد الموافقة، لا في رسالة أو SQL أو command line
أو ملف داخل المستودع. لا يلزم مفتاح Neon إداري في التطبيق ولا مفتاح IA حقيقي.
البيانات المتبادلة مع الهوية: حالة OAuth وnonce وPKCE، رمز authorization قصير،
claims/subject لحساب مختبر اصطناعي، tokens محفوظة مشفرة، وintrospection/revocation.
تُرسل إلى قاعدة الأعمال سجلات الوصفة الاصطناعية فقط. لا كلمات مرور تمر عبر الواجهة
إلى API الأعمال. سياسة الاحتفاظ بوثائق الشركات الحقيقية ما زالت شرطًا قبل العملاء.

المسار الرسمي لإعداد hostname/proxy موضح في
[Keycloak hostname](https://www.keycloak.org/server/hostname) و
[Reverse proxy](https://www.keycloak.org/server/reverseproxy).

   لم تتوفر قراءة حالية موثوقة. القيم السابقة التي أكدها المالك تاريخية فقط.
   لا تعديل لهذه الخدمة ولا لبدء `app.main` أو Health-Only.
2. الموافقة على الموارد والكلفة، وتحديد أصلي HTTPS وشبكات proxy، وإنشاء الخدمات
   الجديدة المنفصلة يدويًا مع منع النشر التلقائي وعدم مزامنة Blueprint حاليًا.
3. تجهيز قاعدة Keycloak مستقلة، ودور runtime بأقل سلطة لازمة، ومراجعة
   `provision-runtime.sql` واختبار رفض DDL/تاريخ Alembic والعبور إلى هدف آخر.
   المنح المقترحة DML عامة على جداول الأعمال، وليست تصميم ACL نهائيًا لـK11.
4. توليد manifest الهوية بالأصل الحقيقي بواسطة الأمر أدناه، مراجعته، ثم استيراده
   صراحة في realm الجديد فقط وتعيين السر ودعوات المختبرين الاصطناعيين.
5. ضبط صلاحية كتابة القرص للمستخدم 10001، والنسخ الاحتياطي للقرص ومفتاحه، ثم نشر
   SHA المراجع وحده. إعادة التحقق من target/role/O4 وبدء التطبيق دون worker أو IA.
6. وصفة دخول من أجهزة فعلية، انتهاء الجلسة، FR/EN/AR وRTL والثيمات، ثم اختبار
   الشركة/المطعم والصلاحيات والـQR. لا يلزم انتظار اكتمال بقية المنصة لهذه المرحلة.
7. إنشاء إعدادات وبيانات اصطناعية صريحة عبر آليات مصرح بها، ثم وصفة الطلب/المطبخ/
   الخدمة/الفاتورة/التسديد/الخروج/التنظيف. لا seed لأسعار ميزات غير معتمدة أو نقد
   أو مستخدم إداري شخصي ضمن نشر الصورة.
8. اختبار التسجيل الذاتي ومزودي الإشعارات/IA والصوت لاحقًا بتفويضات منفصلة.
   غياب النصوص النهائية والأسعار الناقصة يمنع الأعمال التابعة لها فقط، لا الاختبار
   التقني العام. A3 وK11 لهما أدلتهما المستقلة.

مرجع Blueprint: [Render specification](https://render.com/docs/blueprint-spec).
`autoDeployTrigger: off` لا يمنع الإنشاء/النشر الأول عند استيراد Blueprint؛ لذلك
لم يُستورد. لم نطلب أي deployment. سجل عمليات Render الفعلي **غير متحقق**؛ لا
يُستنتج «NO DEPLOYMENT» من غياب أمر صادر عنا.

## 11. أوامر قابلة للمراجعة

الأوامر التالية للتحضير المحلي فقط، وقد نفذت نظائرها في هذه المهمة:

```powershell
Set-Location D:\MoulAI
.\.venv\Scripts\python.exe -I -B scripts/check_staging_preparation.py
Set-Location D:\MoulAI\frontend
npm run build:staging
npm run build
npm run test:guards
Set-Location D:\MoulAI
docker build -f deploy/staging/Dockerfile -t moulai-staging:review-20261110 .
docker build -f deploy/staging/keycloak.Dockerfile -t moulai-staging-identity:review-20261110 .
docker run --rm --network none --read-only --tmpfs /tmp `
  --mount type=bind,source=D:\MoulAI\scripts\check_staging_image.py,target=/tmp/check_staging_image.py,readonly `
  --entrypoint python moulai-staging:review-20261110 -I -B /tmp/check_staging_image.py
```

لإعادة توليد SQL محليًا: `python -I -B scripts/prepare_staging_sql.py`.
يتطلب PostgreSQL 18 المحلي ومنفذ 55434 فارغًا، وينشئ مجلدًا خاصًا جديدًا ويوقف
العنقود الذي يملكه. لا يُستعمل على بيانات دائمة، ولا يُعاد فوق أدلة معتمدة دون
أرشفتها ومراجعة بصماتها أولًا.

لتوليد realm لاحقًا: `prepare_staging_identity.py --origin` مع الأصل HTTPS الفعلي،
و`--client-id` و`--audience` و`--output` لمسار جديد. غياب الأصل الحقيقي يمنع تقديم
manifest مستورد زائف. المشغّل `run_staging.py` يفحص الإعداد افتراضيًا؛ `--serve`
خطوة تفعيل منفصلة بعد الموافقة.

ملفا SQL البعيد محميان بهدف محدد وبحالة البداية. الهدف الحالي O4؛ إعادة تشغيلهما
الآن يجب أن تفشل. عند إعادة تجربة استرجاع في فرع جديد يلزم manifest وبصمات وهوية
فرع مراجع جديد، وليس توسيع allowlist أو تجاوز الحواجز. المثال التشغيلي المستقبلي
يستخدم خدمة libpq خاصة خارج Git، بلا URL أو كلمة مرور في الوسائط:

```powershell
psql 'service=moulai_staging_migration' -X --set=ON_ERROR_STOP=1 --single-transaction `
  --file=deploy/staging/migrations/from-s1a-to-o4.sql
```

لا يُنفّذ هذا المثال على الهدف O4 الحالي. المسار الذي نُفذ فعليًا كان معاملات
Neon MCP الرسمية؛ رفضت المراجعة الآلية تمرير credential عبر أداة طرفية، فلم يُرسل
ولم يُحفظ في ملف. لا تعد تلك المحاولة اتصال SQL أو نجاحًا في مشغّل مستقل.

## 12. الاسترجاع وحدود فقد البيانات

- نقطة ما قبل الانتقال: `br-icy-mud-b9gz0c41` / `ep-cool-hill-b9hnry56`، S1a،
  61 جدولًا؛ تم إثبات تطابق كامل لبصمات الصفوف قبل O4 وبعده.
- قبل قبول بيانات الوصفة، يمكن إعادة إنشاء فرع من هذه النقطة ثم تطبيق الانتقال
  المراجع. لا استرجاع تلقائي داخل التطبيق، ولا تجاوز لحاجز O4 بـstamp.
- بعد أي كتابة اختبارية جديدة، تُوقف الكتابات وتُحفظ نسخة من الحالة الحالية
  أولًا. لا رجوع تلقائي إلى S1a بما يفقد السجلات؛ تُراجع نقطة الاستعادة وRPO
  والآثار المالية الاصطناعية ويُقرر roll-forward أو restore صريح.
- فرع الاسترجاع محفوظ ولا يعتمد على نافذة PITR ذات ست ساعات وحدها. يحتاج لاحقًا
  سياسة احتفاظ/تنظيف محددة، دون حذفه آليًا في هذه المهمة.
- استعادة قاعدة الأعمال لا تستعيد قاعدة Keycloak أو القرص المشفر. يجب نسخ تلك
  الموارد ومفتاح Fernet أيضًا واختبار استرجاعها قبل وصف الاسترجاع الشامل بالناجح.

## 13. مصفوفة الإغلاق

| المطلوب | المنجز | المتبقي |
| --- | --- | --- |
| حفظ GitHub | نسخة العمل محفوظة؛ دفعة التحضير محفوظة في فرع مستقل عند التسليم | لا دمج مطلوب |
| فحص التطوير البعيد | هوية/مخطط/إحصاءات `neondb_test` بقراءة فقط | لا ترحيل عليه ضمن هذه المهمة |
| خطة ترحيل على فرع معزول | منفذة فعليًا مع rollback ونقطة استرجاع | منح runtime واختبار بدء التطبيق على المضيف |
| حزمة staging | صورتان، build مستقل، target، realm generator، Blueprint | قيم الأصل والأسرار والموارد وموافقة الميزانية |
| إعدادات الاستضافة الحالية | غير متحقق منها حاليًا | قراءة Render المصرح بها قبل التفعيل |
| أجهزة فعلية وتكاملات | خطة وصفة محددة | بعد التفعيل المصرح؛ لا ادعاء نجاح مبكر |

المراجعة الآلية منعت أيضًا الوصول إلى نافذة متصفح غير محددة بوصفها Render؛ لم
تُقرأ صفحات شخصية ولم يُلتف على الرفض. بقيت إعدادات Render الحالية والتكاملات
الإدارية غير متحققة. هذا تحفظ على التفعيل، لا سبب لإهدار التجربة المعزولة المنجزة.

**الخلاصة: التحضير والترحيل التجريبي منجزان مع تحفظات معلنة؛ نشر staging يحتاج
قرار موارد وتفعيل منفصلًا. لا إعلان جاهزية إنتاجية ولا انتظار لاكتمال كل شيء قبل
بدء اختبار بعيد مغلق.**
